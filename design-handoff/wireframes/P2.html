의도

목록으로 훑고 도식으로 다듬는다. 두 방식의 약점이 서로를 메운다. 목록만 있으면 아홉 줄이 부담스럽고, 도식만 있으면 무엇을 정할 수 있는지 모른다. 먼저 목록에서 전체를 한 번 보여 주고, 그 결과를 도식으로 가져가 눈으로 확인하며 만지게 한다.

화면을 둘로 나누지 않고 한 화면의 두 상태로 둔다. E1 - P1 - P2 - W1 만으로도 이미 네 단계인데 여기서 더 늘리면 진입이 길어진다. 상단 전환 버튼으로 오간다.

컨셉이 정한 항목에 표시를 단다. 아홉 개가 전부 같은 무게로 보이면 어디를 봐야 할지 모른다. 컨셉이 의도를 담아 정한 것이 무엇인지 보이면, 사용자는 그것부터 확인하고 나머지는 넘긴다.

기본값이 다 채워져 있고 아무것도 안 건드려도 진행된다. 컨셉을 고른 의미가 여기 있다. 빈칸에서 시작하면 컨셉이 한 일이 없어진다.

여기서는 API 를 쓰지 않는다. 전부 플래그 조작이라 비용이 0 이다. 그래서 마음껏 눌러 볼 수 있고, 그 점이 W1 과 결정적으로 다르다. 대화로 물어보면 매번 비용이 들지만 여기서는 안 든다.

도식에 속하지 않는 것 - 색, 글꼴, 기능 - 은 도식 상태에서 아래에 따로 둔다. 억지로 도식 위에 올리면 어디를 눌러야 할지 오히려 헷갈린다.

바꾼 것을 모아 보여주고 되돌릴 수 있게 한다. 많이 바꿨다면 컨셉이 맞지 않는다는 신호이므로 그 사실을 알려 준다.

컨셉으로 되돌아갈 때 이미 만든 4안 중에서 고르는 것은 비용이 들지 않는다는 점을 밝힌다. 조건부터 바꾸면 재생성이라 비용이 든다. 둘을 구분해야 사용자가 겁내지 않는다.

대안

  • 보편 B 묶음별 하나씩 - 매번 결정이 가볍지만 네 번 넘겨야 한다. 사이드바 하나만 바꾸려는 사람에게 세 화면이 낭비다.
  • 실험 B 이 화면을 만들지 않기 - 진입이 가장 짧지만 무엇을 바꿀 수 있는지 모른 채 대화만 하게 된다. 그러면 플래그 하나 바꾸는 데도 매번 API 를 태운다. 비용이 사용자 부담인 이상 이건 손해다.
  • 목록과 도식을 동시에 크게 놓기 - 화면 폭이 모자란다. 목록 상태에서 작은 도식을 옆에 두는 것으로 절충했다.

미정

  • 항목 아홉 개를 다 보일지, 컨셉이 건드린 것만 앞에 두고 나머지를 접을지. 지금은 다 보이되 표시만 달았다.
  • 결정됨 - W1 에는 세부 패널을 두지 않는다. 경로가 둘이면 같은 것을 두 곳에서 고칠 수 있게 되어 어느 쪽이 최신인지 헷갈린다. W1 에서 세부를 바꾸고 싶으면 대화로 말한다.
  • 도식에서 누를 수 있는 영역을 어디까지 나눌지. 사이드바, 목록, 본문 셋 정도면 충분할지.
  • 강조색 직접 고르기를 어느 수준까지 줄지. 색을 자유롭게 열면 읽기 어려운 조합이 나온다.
